# Changelog

Per-version change history for the `cortex-platform-xdm-author` bundle. The current version is declared in the `SKILL.md` frontmatter; this file is not loaded at runtime and exists for provenance.

## 2.0.0

The first public release since 1.8.1, and a major rather than a minor because this bundle now judges a rule differently from the one that shipped. A pre-ship review then found three artefacts contradicting the rules they exist to enforce.

WHY THE MAJOR. Two changes between 1.8.1 and here are breaking by any reading. `xdm.auth.service` reversed meaning in 1.9.0 -- it is the ROLE the system played, and a rule that correctly wrote a service name under 1.8.1 is now flagged by WARN-042. ERR-029 through ERR-034 turn constructs that linted clean under 1.8.1 into blocking errors; each was isolated by live-tenant bisection and each fails a pack install with an opaque 101704, so the checks are right, but a rule that passed then can fail now. A fifteenth mandatory authentication field, `xdm.target.resource.name`, landed in 1.8.23. The version number is the only thing that carries this to someone who pinned, and 1.9.1's own entry records the cost of it not doing so: a FortiGate rule authored in full against superseded guidance, caught by accident from a merge commit message in another repository.

SAMPLE DATA. Every hostname in `tests/fixtures` and `tests/corpus` now resolves under a reserved documentation domain, and a guard enforces it: RFC 2606 and RFC 6761 names, the two synthesised estates the worked examples declare, and the cloud providers' own API endpoints pass; anything else fails the suite. Java and .NET class names are matched and dropped before the hostname rule sees them, since `java.net.ConnectException` is a hostname read backwards. Sample data is synthesised, as `references/worked-examples.md` states, and this makes that a property the suite checks rather than a convention it trusts.

THREE ARTEFACTS THAT CONTRADICTED THE RULES THEY ENFORCE. Each was a hard rule stated in one place and inverted in another, and in every case the shipped tooling settled which was right:

- `references/pitfall-traps.md` told the author "The first stage of the rule MUST be `alter`. Do NOT prefix the rule with a `filter` stage of any kind", and printed `filter _raw_log != null` under a WRONG banner. That opening is mandatory: SKILL.md prescribes it, `scaffold_rule.py` emits it, `clean_rule.xql` and the shipped Pattern D rule both open with it, and the linter passes it. Nor is the predicate a tautology, since a dataset carries null `_raw_log` records whenever the fields arrive as pre-parsed top-level columns. Rewritten to say what is actually forbidden: a tautology, a re-assertion of the dataset selection the MODEL header already made, and any predicate that drops records rather than routing them to the catch-all.
- `scripts/scaffold_rule.py` padded the three `xdm.network.http.*` leaves on every network-flagged sample, so a plain syslog feed came back asserting `url_category = URL_CATEGORY_UNKNOWN`. SKILL.md forbids exactly that by name and `lint_rule.py` gates WARN-043 on `_rule_claims_http_layer`. The leaves now sit behind the same gate, held deliberately identical to the linter's definition. The test that should have caught it asserted the defect instead, requiring `url_category` on a firewall flow with no URL in it.
- `assets/modeling_header_template.xql`, the asset every emitted rule copies, told the author to describe the rule as reading parser-stamped `_` anchor columns through `coalesce()`. That read is out of scope and `lint_rule.py` blocks it as ERR-027. Replaced with the inverse statement. Worked example 05 carried the same residue in one bullet while its own printed rule used `json_extract_scalar`.

CLAIMS THAT MEASUREMENT DID NOT SUPPORT. SKILL.md's step 8 restated the linter's code list and had fallen eleven codes behind it; the guard that existed for this scored the line as two codes, because `ERR-009/010/011` is one regex match and the rest carry no prefix. README.md said ERR-019 is scoped to `_gc_raw` datasets, against `lint_rule.py`'s own docstring -- Cortex rejects an unused field regardless of suffix, and only ERR-025 is scoped. Three places prescribed assigning a bare `concat()` to `xdm.alert.risks`, which is `String (Array)`; linting the exact shape returns WARN-035, and SKILL.md already called this "the `xdm.alert.risks` expected array defect" one section earlier. The 645-field schema count was inherited from 1.5.2 and is 628 on disk. `modeling-rules.md` cited WARN-019, WARN-020 and WARN-010, none of which exist, and described the linter as covering a syntactic subset needing manual review first, which stopped being true when the schema and dataflow passes went offline. `pitfall-traps.md` filed `xdm.event.tags` under "groups with no enumerated constants" and said to omit it, when EVENT_TAG is fully enumerated and mandatory in both story sets.

WHAT LEFT THE BUNDLE. The public changelog named the private documentation tree and two of its script paths; a reader of this repository can open neither, so the citations published a layout while adding nothing. Two tests reached two directories above the bundle into that tree and guarded with `if path.is_file()` rather than `skipTest`, so for every public user they ran and asserted nothing while reporting ok -- both now assert against the shipped references that carry the same facts. One dataset name appeared in a compatibility note and nowhere else in the bundle or in any vendor index; the sentence did not need it. `references/virtualization-mapping.md` is held back rather than shipped: it self-declared provisional and unconfirmed against any tenant, carried open questions, and nothing linked to it, so the only way to reach it was to list the directory.

GUARDS, BECAUSE EVERY ITEM ABOVE WAS INVISIBLE TO 517 PASSING TESTS. Sample data must use documentation domains. Every version stamp must equal the SKILL.md frontmatter, which is what the template's two-release drift at 1.8.24 defeated. README's code list is compared to the linter in both directions. No reference may cite a code the linter lacks -- that guard found a fourth phantom on its first run, which turned out to be a Cortex IDE validator code and is exempted by name. The documented field count must equal the list on disk. Every file in `references/` must be reachable from SKILL.md, README.md or another reference.

## 1.9.1

Three fixes from a FortiGate CEF rule, all in ERR-034's orbit. The first is the bundle prescribing a remedy its own verifier could not read.

- FIXED: `verify_rule.py` could not tokenise a backtick-quoted column. ERR-034 tells an author to escape a reserved column name as `` `in` ``, SKILL.md calls that the escape "which 328 shipped upstream rules use and never omit", and `lint_rule.py` accepts it -- and then the verifier died with `cannot tokenise near: '`in`)'`. So following the bundle's own remediation made a rule impossible to verify offline. That is worse than a nuisance, because `--coverage` and `--prepend-check` are the ONLY offline proof steps in the workflow, and any CEF source with an `in` or `out` column silently skipped both. The tokeniser now has a backtick-quoted identifier, and it deliberately does NOT keyword-match the result: the whole point of the quoting is that `in` there is a COLUMN, not the membership operator, and emitting a `kw` token would have the parser read an operator where the author wrote a field.
- `in` is now RESERVED, and the reason it was not does not survive measurement. Until now this bundle recorded it as excluded "because it is also the membership operator and flagging it would fire on every `action in (...)`". That was true of a cruder check and is false of the current one: the read patterns only match in VALUE position -- after `=`, `(` or `,` -- and the operator never appears there, it follows an identifier. Re-measured against the corpus exactly as the check runs, with strings and comments stripped: 570 membership-operator uses of `in`, ZERO matched, and 9 backticked reads the check correctly accepts. That is the same evidence shape as every other member of the set, and it was a reason recorded once and never retested.
- `out` is NOT reserved, and that is the more interesting half. It arrives paired with `in` on every CEF firewall, so symmetry makes it tempting. The corpus refuses: `out` is read BARE in value position 8 times in shipped upstream rules -- `to_integer(out)` on the sent-bytes mapping -- and never backticked. That is the `timestamp` (39 bare) and `dst` (146) pattern, not the `target` pattern. Reserving it would invent a hazard and would call 8 rules broken that demonstrably install. A pair is not evidence about both halves.
- `lint_rule.py` now reports the bundle version on every run, to stderr, and takes `--version`. An author cannot otherwise see which bundle they are linting against, and the recommended pinned-worktree practice freezes them on whatever was current when they pinned. That is not hypothetical: a FortiGate rule was authored in full against 1.8.24's `xdm.auth.service` guidance while 1.9.0 reversed it on main, and nothing in the authoring path said so -- it was caught only from a merge commit message in a different repository. The version goes to stderr rather than into the JSON so the stdout contract other tooling parses is unchanged.
- Synced `RESERVED_COLUMNS` in the content-pack bundle's `scripts/preflight_release.py`, which gates the same fault at upload time and carries a note that the two must not disagree. While there, made its three patterns case-insensitive, which `lint_rule.py` already was. XQL folds case, so `to_number(IN)` passed that gate and failed the install -- precisely the disagreement the note warns about, sitting inside the check the note is attached to.

## 1.9.0

Reverses this bundle's rule for `xdm.auth.service`. It is a ROLE field, it always was, and the correction that said otherwise was itself the error.

- `xdm.auth.service` carries the ROLE the system played in the authentication flow, decided PER EVENT TYPE: `"IDP"` when it validates the credential, `"SP"` when it initiates and relies on another to validate, `"Universal"` when the source is not a known IdP provider. It is never a service name. The official page "XDM fields for mapping authentication events" states this in the field's own description -- "the role the system played in the authentication flow, such as identity provider or relying party" -- and has done throughout.
- THE FAILURE WAS A NON-SEQUITUR, and that is the part worth keeping. In 1.8.x a dated "correction" declared `"SP"` / `"IDP"` a retired v1 inference with "no such XDM values", reasoning from the schema's plain `String` type to the absence of a vocabulary. A String-typed field can still carry a documented closed vocabulary. Nothing in the schema contradicted the page; the two describe different things, and one was read as refuting the other.
- The correction did not stay in the docs. It became a linter check that flagged the CORRECT value as deprecated, a scaffolder that seeded `"Login"`, six worked examples, a test asserting the wrong behaviour was right, and nine shipped packs. It also became a pair of gates in the corpus-mining tooling that discarded upstream `"SP"` / `"IDP"` assignments as a policy conflict -- so the corpus, which held the answer in Okta, IBM Security Verify, Silverfort, Duo, Salesforce, Slack and OpenAI, was structurally unable to correct us. A wrong claim that teaches the evidence-gathering step to reject its own counter-evidence is the expensive kind.
- The role is per EVENT TYPE, not per data source, and the distinction is load-bearing. On an Okta feed Okta emits every record and validates every credential, yet upstream maps `eventType = "user.authentication.sso"` to `"SP"` and the credential-validation events to `"IDP"` (`OktaModelingRules_2_0.xif:97`). The subject of the role is the leg of the flow the event names, not the emitter. A rule that classifies records into authentication and non-authentication kinds sets the role only on the authentication branch.
- WARN-042 now accepts the role vocabulary and flags a service name in its place. Matching folds case, as XQL does. Severity stays advisory, deliberately: ERR is reserved in this bundle for tenant-confirmed install-blockers, and `xdm.auth.service = "SSH"` installs cleanly and fails silently downstream. The WARN-047 -> ERR-030 precedent requires evidence that an advisory FAILED, and there is none here -- the shipped packs are wrong because the guidance was wrong, not because a warning was ignored. PROMOTION TRIGGER, recorded so it is a commitment rather than an intention: if a rule authored after 1.9.0 introduces a non-role value and the advisory did not stop it, that is the evidence, and the check becomes a blocking error.
- The check reads `if()`-chains, not only bare literals. A value-conformance check restricted to self-contained literals would have been nearly inert here: twelve of the thirteen assignments in our own shipped packs come from an `if()`-chain, so the earlier check could not see them. It now walks the chain's VALUE positions -- the odd arguments plus a trailing default -- so a predicate literal is never reported as a returned value, and `coalesce()` is read the same way. A chain that already returns a role on some branch is left alone, because a mixed chain may carry a deliberate passthrough the linter cannot evaluate.
- `xdm.auth.service` moved from the scaffolder's paddable set to its must-extract set. A role decided per event type cannot be seeded with a default without asserting a flow shape the scaffolder cannot know, which is the same argument that made `xdm.target.resource.name` a must-extract in 1.8.23. The `"Login"` pad is gone entirely: it stood in for a missing service field, and under the role reading there is no such thing to be missing.
- Where the displaced detail goes, on a wire-versus-mechanism split. The layer-7 protocol carrying the session goes to `xdm.network.application_protocol` (`ssh`, `telnet`, `snmp`, lowercase App-ID form, as upstream `VMwareESXi_2_9.xif:262` and `LinuxEventsCollection_1_3.xif:104-106` do); how the credential was checked goes to `xdm.auth.auth_method` (TACACS+, RADIUS, LDAP, an IdP connection name); an authentication PACKAGE goes to `xdm.logon.package_name`, whose description is exactly that and which upstream already fills with Kerberos / NTLM / Negotiate (`MicrosoftWindowsEvents_1_3.xif:165`). They coincide only when the AAA protocol IS the session, and then both are set. An access channel (CLI, GUI, Dashboard, API) goes to `xdm.target.application.name` and is BARRED from `xdm.event.operation_sub_type`, whose authentication vocabulary is a closed list that a channel value corrupts.
- `"Universal"` is house law and is registered in `references/house-conventions.md`, not asserted as schema fact. The published page lists two values; the third is ours, its source is deliberately not reproduced, and the entry says so and tells the next author NOT to remove it on the strength of the page. The counter-evidence is recorded in the same entry rather than omitted: upstream maps `auth_via_radius` to `"IDP"`, and the vendor's own role chain terminates in `null`, so both "RADIUS is an IDP" and "leave it unset" are arguable positions. An author who disagrees has what they need to argue.
- `references/house-conventions.md` used this field as its worked example of an inference mistaken for schema fact, with the direction reversed. Corrected, and it is a better example now: the unmarked claim was the correction, not the thing corrected.

## 1.8.24

A fourth install-blocker, ERR-034, and the escape for it that the corpus turned out to have been using all along.

- Added ERR-034. It flags an UNQUOTED read of a raw column whose NAME is a query-language construct. The READ is the fault, not the assignment: `alter tmp_v = api_key_id` installed, and adding `tmp_view = view` failed the whole pack install -- two uploads differing by one line, with an opaque 101704 naming no field and no line, while the linter passed, `spellbook validate` passed, the modelling schema declared the column and the same read ran perfectly in SEARCH mode. This also corrects a claim this bundle made about its own convention: the `tmp_` prefix avoids half the reserved-word class, not all of it. It protects the name a rule CREATES, and this is the name a rule READS -- `tmp_view` was correctly prefixed and still fatal.
- THE ESCAPE IS A BACKTICK, and the check demands it rather than forbidding the column. That was measured rather than deduced, and re-measured on the way back in: across the shipped upstream corpus these columns are read inside backticks and never bare -- `target` 31 times, `fields` 13, `in` 10, `transaction` 6, and `tag`, `table` and `filter` twice each. So an in-rule fix does exist. Renaming the column at source is still preferred where you control what writes it, because the backtick must be repeated at every read and a missed one fails the same silent way.
- The flagged set was derived from that corpus rather than from how SQL-ish a word looks, which is a bad guide. Reserved: `view` and `tag` (confirmed by live-tenant bisection) plus `target`, `fields`, `transaction`, `table` and `filter` (never read bare in any shipped rule). `in` is excluded despite qualifying, because it is also the membership operator and flagging it would fire on `action in (...)`. Matching folds case, since XQL does. Measured at zero false positives across 387 upstream rule blocks and all 53 of our own, with 66 backticked reads present that the check correctly accepts, so the zero is not vacuous.
- CORRECTED a control-word claim the earlier version of this work stated and the content-pack gotchas still carry. That version said `contains` is "read bare 1485 times in shipped rules" and `call` 474, offered as proof those names are ordinary. They are occurrence totals, not column reads: `contains` appears 1429 times and 1428 of them are the OPERATOR, with ZERO value-position reads. The corpus holds no column called `contains`, `call` or `values` at all, so it neither supports nor refutes reserving them -- they are excluded for want of evidence, which is a weaker claim than measured-safe. Only `timestamp` (39 bare reads) and `dst` (146) are actually demonstrated ordinary. Re-measuring rather than restating is what surfaced this.
- Evidence across the reserved set is uneven, and the comment now says so. `target` is attested by 31 backticked reads across 12 vendors, `fields` 13, `in` 10 across 10 distinct rules, `transaction` 6; `table` and `filter` rest on 2 each; `tag` on 2; and `view` does not appear in the corpus in ANY form. The two thinnest are exactly the two confirmed by live-tenant bisection, which is why bisection was needed. Corpus silence is not evidence of safety.
- The reserved set is held deliberately identical to `RESERVED_COLUMNS` in the content-pack bundle's `scripts/preflight_release.py`, which gates the same fault at upload time. The two must not disagree: a rule this check passes and that gate rejects costs a burned version number per upload.
- Fixed `_strip_line_comment` losing its place on an escaped quote. The walker toggled its in-string state on every `"`, so a line carrying `\"` -- `trim("@element", "\"")` is the common shape -- left it believing it was inside a string, and every `//` after that read as code. Every check that strips line comments was affected, not just the new one.
- ERR-034 also strips `/* ... */` block comments, which nothing else in the linter does. Upstream rules carry long block headers describing the very fields they map, so a check that scans for identifiers cannot read them as code. The blanking preserves newlines, so line numbers after a block comment stay correct. The rest of the linter still cannot see block comments, which is a gap rather than a decision.
- Note on provenance: an earlier attempt at this work also carried the number 1.8.23 and was lost uncommitted before it reached any branch. This is a rebuild from the surviving design record, not a restore, and every empirical claim above was re-measured against the corpus rather than carried over on trust.

## 1.8.23

A fifteenth mandatory authentication field, because the fourteen we had could all be assigned on a rule that had the login pointing the wrong way.

- `xdm.target.resource.name` is now MANDATORY on any record classified as authentication: the device, application or service the principal authenticated TO. An authentication event has a direction, and nothing in the mandatory set recorded it. CiscoIOSXR 1.0.7 is the proof -- it linted completely clean across 764 SSH login records with every one of the fourteen fields assigned, while every record was inverted, the accessed router having been mapped to `xdm.source.host.hostname` when the router is what is being logged INTO and the source is the administrator's workstation. The linter had nothing to say, because WARN-042 checks whether a field is ASSIGNED, not whether the right entity landed in it. Naming the target is the step at which the inversion becomes visible.
- THE FIELD IS NEVER PADDED, and that is the load-bearing half of the change rather than a detail. Every other unmapped member of the set has an official placeholder; this one does not, and WARN-055 flags a placeholder if one appears. The general rule in this bundle is to pad only where the placeholder is semantically EMPTY, and the target block now shows both sides of it in one stanza: `xdm.target.ipv4 = ""` honestly says an IdP record has no target address, while `xdm.target.resource.name = ""` would say the target is known and is nothing, which is never true. A padded target field is precisely the state an inverted rule passes the linter in, so a check satisfiable by padding would have certified CiscoIOSXR too. The scaffolder therefore emits it as a must-extract TODO, never a seeded value.
- WARN-055 flags PLACEHOLDERS, not constants, and the distinction was deliberate rather than conservative. A dedicated SSL-VPN portal or console feed really does have one constant target, so `"AWS Console"` is information and is accepted; `""`, `"-"`, `"N/A"`, `"unknown"` and their kin are not. Flagging every literal would have fired on the honest cases and taught authors to mute the checker, which is the failure mode the network HTTP set was already scoped to avoid.
- Dual-mapped, never re-routed. The type-correct target field keeps its mapping and `xdm.target.resource.name` is set as well, so a router still takes `xdm.target.host.hostname`, an application still takes `xdm.target.application.name`, and asset correlation is unaffected. Shipped practice already did this: the Imperva pack sets `xdm.target.host.hostname` for a Site while `xdm.target.resource.name` keeps the logical name.
- This supersedes the cloud-only reading of `xdm.target.resource.*` in pitfall-traps.md, for authentication events only. That reading was this bundle's convention rather than schema truth -- the canonical schema says "The resource name", optional String, no enum -- and the anchor corpus disagrees with it too, carrying `devicename` and `applicationname` among the observed synonyms at frequency 85.
- Added `references/house-conventions.md`, a register of the places this bundle requires MORE than the schema does, each entry stating the platform position, our reason, and what evidence would retire it. It exists because of what this same file records about `xdm.auth.service`: a house inference that the field held an `"SP"`/`"IDP"` role token was written down as though it were schema fact, authors inherited it, and unwinding it took a dated correction plus a linter check that still ships. Nobody could evaluate the claim because nothing marked it as a claim. A convention is not weaker than a schema rule here -- the linter enforces both -- it is just accountable.
- Migrated the five auth worked examples that needed it. In three the value was already extracted and then discarded: Entra had `appDisplayName` going into `xdm.auth.service` and `resourceId` used only to build a description string, and Windows had `ServiceName` parked in the NOT MAPPED block awaiting a 4769 branch that was never written. Okta already complied and is the exemplar. That Entra case also names the quieter symptom this change fixes: because the target had no mandatory home it had been leaking into `xdm.auth.service`, which is meant to hold the authentication protocol -- `appDisplayName`, `"AWS Console"` and `"SSL-VPN"` are all targets, not protocols.
- Corrected a stale field count in transformation-patterns.md, which had said 12 and was already wrong against the previous 14.
- Note on this version number. An earlier, unrelated 1.8.23 was in progress and never shipped: ERR-034, blocking an unquoted read of a raw column whose name is a query-language construct, with the backtick escape measured across 328 upstream rules. It was lost uncommitted when a concurrent session reset the working tree to origin/main, was never committed to any branch, and is not recoverable from this repository -- so the number was free and is reused here. ERR-034 itself still needs redoing from the live-tenant bisection that produced it, and will take the next number when it does.

## 1.8.22

Three install-blocking constructs, and the removal of a lookahead this bundle shipped twice.

- Added ERR-031, ERR-032 and ERR-033. All three block a pack install with an opaque 101704 that names no field and no line, or (ERR-033) never return at all; none was visible offline; all three were isolated by bisection against a live tenant; and each measures at ZERO false positives against a corpus of shipped rules.
- ERR-031 flags an `XDM_CONST` member that does not exist. The trap is that the closed lists look like well-known external enumerations and are not: syslog severity has eight levels and the XDM log-level list has five, six of the eight share a name, so writing the remaining two reads as completing a table rather than inventing a constant. There is no EMERGENCY, no ALERT and no DEBUG -- floor 0 and 1 to CRITICAL and 7 to INFORMATIONAL. Likewise there is no logout verb: a logout is not a login, so leave `xdm.event.operation` unset and let `xdm.event.type` and the vendor token carry it. The check is scoped to families this bundle documents COMPLETELY, established by measuring the reference against the corpus -- `IP_PROTOCOL`, `OPERATION_TYPE` and `IDENTITY_TYPE` are deliberately NOT gated, because there the reference is a subset and flagging would report our own incompleteness as the author's error. The four members proven absent on a live tenant are listed explicitly so they are caught regardless.
- ERR-032 flags a `regextract` with more than one capturing group. The shape is natural -- a Cisco ACL line puts an address and its port adjacent, so capturing both in one pass reads as economical -- and it is also silently pointless, because `arrayindex()` reads one element and the second group was never going to be used. The group counter ignores escaped parentheses, `(?:` groups and parentheses inside a character class, so a pattern whose only parentheses are literals inside a character class counts as one group, not three.
- ERR-033 flags a lookahead or lookbehind. This engine does not support lookaround and does not report that it does not: the query HANGS. Measured back to back on one dataset, the control returned in about ten seconds and the lookahead version was still running twelve minutes later with no result and no error. That is worse than a rejection, because the caller sees a timeout and reads it as a crash in whatever ran the query -- and the stall appears to belong to whatever ran BEFORE it.
- REMOVED the lookahead this bundle shipped. Recipe 15 (1.8.19) used `(?!SLOT\d)` to exclude the card wrapper and the syslog envelope (1.8.17) used `(?![^<]*<\d{1,3}>)` to guard the relay tag. Neither would have run. Recipe 15 loses nothing material: a card wrapper PRECEDES the real token, so the greedy `.*` already skips it, and the only case the lookahead added was a wrapper carrying no inner message, which by definition contains no event. The syslog guard has no replacement -- there is no regex answer on this engine -- so the guidance now says plainly not to derive a process tag from the line on a source that emits tagless records behind a relay, and to record that in the MAPPED header instead of padding it.
- Added the one outlier to the story gate that should keep its tag. Cisco IOS SSH transport failures (`SSH-3-NO_MATCH`, `SSH-4-DH_RANGE_FAIL`) are genuinely authentication events that genuinely cannot fill the authentication story: they are algorithm negotiation failures, so they happen BEFORE any principal exists. The discriminator is not "is a principal present" but "could this event, BY ITS NATURE, ever have had a principal". A negotiation failure never could; a login that merely lost its username to a bad capture always could, and that is the case the gate exists to catch. Stripping the tag from the first would hide a real authentication failure from the story that exists to hold it.

## 1.8.21

CIDS and WPS: two security facilities that do not log the security event.

- Mined CIDS (11 messages) and WPS (57), and both are the facility-name false friend in its sharpest form. CIDS is the external IDS/IPS sensor integration and every one of its eleven documented messages is a failure -- severities 1 and 3 only, no informational member at all, and NO successful-shun record anywhere. WPS is the Wireless Protection System and 52 of its 57 messages are signature-FILE PARSING errors. The enforcement both facilities exist to perform is emitted elsewhere: by the mobility manager (`MM-1-CLIENT_SHUNNED`) and the policy layer (`APF-*` rogue and exclusion records).
- Generalised it in record-classification.md, because one controller now supplies three instances -- SSHPM owns SSH policy and logs no logins, CIDS owns IDS integration and logs no shuns, WPS owns wireless protection and logs mostly file parsing. A facility name tells you which subsystem OWNS a feature; the event is frequently emitted somewhere else. Find an event by reading TEMPLATES, never by reading facility names. The failure mode is quiet and expensive: a rule keyed on the plausible facility lints clean, classifies records, and reports zero detections forever, because the facility it modelled genuinely never emits any.
- Recorded the inverse value. A security facility that logs only its own failures is telling you the control is not working: `CIDS-1-SHUN_LIST_ENTRY_CREATE_FAIL` means a sensor asked for an enforcement and the controller could not apply it, so the client stayed connected. That is a control failure and it is more urgent than most of the detections it sits beside.
- Documented the split alarm. `WPS-4-SIG_ALARM_OFF` carries the detecting AP, the signature, the track mode, the precedence, the hit count, the slot and the channel -- everything except who did it -- and the offending station's MAC arrives in a separate `WPS-4-SIG_ALARM_OFF_CONT` record beginning `...continue`. Model only the first and the result is a detection with a detector and no subject. The continuation carries no signature identity of its own, so correlation is by adjacency. This is the third instance of an event split across records, after the Cisco `**MSG ... CONTINUATION #YY` form and the Nokia NFM-P header-less line, and the check is now stated once: before mapping a record, ask whether the event is CONTAINED in it.
- Noted that `SIG_ALARM_ON` does not appear in the guide at all. The alarm CLEAR is documented and the alarm RAISE is not, so a rule built from the catalogue models the end of a signature match and never the start of one. Confirm the raise form against real data rather than assuming it does not exist.
- Added the CAPWAP join-rejection subset while adjacent (`DISC_MAX_JOIN`, `INVALID_MSG`, `INVALID_PAYLOAD`, `INVALID_PREAMBLE`). ## 1.8.17

Greedy is not the same as last, and a block splitter that lost every dataset name after the first.

- Recorded that a greedy `^.*` prefix is NECESSARY but NOT SUFFICIENT for relay-prepended syslog. Greedy makes the engine PREFER the last place the pattern can match, which on a relayed line is the origin's copy -- but only while the origin satisfies the whole pattern. Where it does not, the engine backtracks rather than giving up, and the relay's copy has the same shape by construction, so the relay wins and the field silently reports the relay's value. This makes greedy alone wrong for any field that can be ABSENT from the origin record, of which the process tag is the common case, because a tagless record is ordinary.
- The fix is to assert what must NOT follow the capture rather than to make the anchor more specific: `\[\d+\]:(?![^<]*<\d{1,3}>)`. Re-anchoring on a fuller RFC 3164 header is the intuitive next move and is worse -- the relay's own header matches that shape exactly as well as the origin's, so backtracking still reaches it, and it additionally breaks on a relayed line whose origin priority was stripped, where the looser form had succeeded.
- Corrected a false claim in the same reference. The "when the priority is stripped" section said the Stage 0 host captures return null. That holds on a DIRECT line; on a RELAYED line the relay supplies a priority of its own, the origin no longer has one to be preferred, and the captures silently become the RELAY's host and priority. That arrival form is the one Stage 0 as written does not survive, and it is now stated rather than implied otherwise.
- Fixed a block-splitting defect in both `lint_rule.py` and `verify_rule.py`. The block start was `^\s*\[MODEL:`, and `\s*` also matches the preceding newline, so a block with a blank line in front -- the normal way to format a multi-block rule -- began on that blank line. The dataset name was then parsed from an empty string and came back null, so every block after the first lost its name: `--dataset` could not select it, and the linter labelled its findings with no dataset at all. Anchoring on horizontal whitespace only (`^[ \t]*\[MODEL:`) fixes both tools, and a commented-out `[MODEL: ...]` line in a MAPPED header is still correctly ignored.
- `SKILL.md` now names the `prepend_check` key of the verifier's JSON result, so a caller looking for `differences` or `mismatches` does not read an empty list as a pass.

## 1.8.15

An advisory that assumed two fields described the same thing.

## 1.8.14

Two checks that were asking for the wrong thing.

- Fixed an INFO-013 false positive on a gate temp. The check counted the XDM categories a temp was "mapped across" by scanning the whole right-hand side, so it followed the temp into the CONDITION argument of an `if()` as well as into the value positions. A boolean gate holds `"y"` or null, is never assigned to any XDM field, and only decides WHETHER a family is padded -- and conditionally padding several families from one gate is the prescribed idiom for claiming a story only where its mandatory set can be populated. The check now counts a temp only where its VALUE reaches a field, so a gate conditioning many families is silent while the same temp used in a value position across three families still fires. ## 1.8.13

A capture that ends where the line ends, and a regex result that is wrong but clean.

- Stated that a capture must terminate on CONTENT, not on the end of the line, wherever the extracted value will be COMPARED rather than merely displayed. A capture running to end-of-line inherits whatever the device put there, and a trailing space after a CLI command is common, so `(.+)` keeps it. The resulting field is populated, non-empty and not the sentinel; it reads correctly in every sample and in a `comp count() by`, and differs from the same value written without the space under exact comparison alone. A filter for the command therefore returns zero rows rather than an error, which means a correlation keyed on a specific command is structurally incapable of matching and fails as an empty result set that nobody investigates. The fix needs no trim function: `(.*\S)` is greedy up to a required final non-space, so it takes the whole value and drops the trailing whitespace. `xdm.target.process.command_line` and `xdm.event.original_event_type` are called out as the fields where this bites hardest, both being natural correlation keys; a free-text description legitimately wants the tail.
- Corrected two shipped rules that had the defect: the SR OS command capture in extraction-recipes Recipe 7 and the sudo `COMMAND=` capture in worked example 11. The Cisco WSA envelope strip was left greedy deliberately -- its result is re-parsed rather than compared, so a trailing space there is inert, and the rule is stated in terms of where it matters rather than applied blanket.

The check is scoped to compared fields by design: flagging every greedy capture would be noise, and a group already closed by a delimiter (`command '(.+)'`) cannot pick up whitespace outside the delimiter and stays silent. Advisory, because a source may be known never to emit trailing whitespace.
- Recorded that the loud escaping failure is the lucky one. A double-escaped metacharacter returns HTTP 500 and announces itself, but a double-escaped character CLASS silently asks a different question -- `\\s` is a literal backslash followed by the letter s, so it matches nothing and returns a clean zero. A clean zero is indistinguishable from a true negative, so it reads as "the condition does not occur here" and closes the investigation. The tool cannot distinguish a sample set that lacks the event from a pattern that was never capable of matching, and says so.

## 1.8.12

Two rules about identity values, which pull in opposite directions and are easy to conflate.

- Stated that an identity field records what was PRESENTED, not what is valid. A rule must not sanitise, normalise, trim or reject an odd identity at model time, and must never substitute the catch-all for an unparseable one. A login attempt whose account is a template-injection payload is a probe typed at the authentication prompt, and it is detectable only because the rule preserved it verbatim; dropping values that fail a shape test, stripping metacharacters or declining to map the field would each have destroyed the evidence.

On this vendor the security application's largest members are a AAA server status change and a routing-protocol digest mismatch, neither of which has a principal; classifying on the application would tag device-status and routing records as user authentication. The digest-mismatch event is called out specifically because its name contains a word a keyword classifier would grab.
- Added routing for command-I/O events to the process family, matching the existing treatment of AAA command accounting: the command to `xdm.target.process.command_line` with `OPERATION_TYPE_AUDIT`, no outcome and no authentication tag.
- Noted that the third syslog token is the TAG rather than the device name, and varies, so a rule that reads it as the hostname gets a constant on a large share of records.
- Added a four-line fixture covering both principal shapes, a record with no principal and a command-I/O record, plus three tests. One asserts directly that the username is never the literal `from`, which would have caught the defect outright.

## 1.8.8

Adds a platform behaviour that has to be a hard rule rather than a gotcha, because the natural way to write the affected capture is the wrong way.

- Documented that XQL matches case-insensitively everywhere -- string comparison, `contains`, `~=` and `regextract` alike -- and stated the consequences. An uppercase character class does NOT restrict a capture: `[A-Z]` also matches lowercase text. `(?i)` is redundant, harmless as a statement of intent but changing nothing, and no rule may depend on case-sensitivity because it cannot be requested. `uppercase(x) = x` is always true, so no query can test for case either; auditing a field for case means reading its distinct values outside the query.
- Added the hard rule that follows: case can never qualify a capture, structure must. An uppercase class is the obvious way to express "this token is a vendor tag, not prose", and it silently does not work -- the capture takes whatever token occupies the position, such as a function name from microcode output. Anchor on structure that identifies the token (the `%` sigil and severity digit, a key name, a quote). Where the position genuinely is free text, enumerate the documented vendor tags in an alternation; those are not the sample-derived literals WARN-049 forbids, being the same class of value as `UI_LOGIN_EVENT`.
- Named the fourth failure state for a mapped field: populated with a plausible but WRONG value. It passes the null, empty and sentinel checks together, so no count reveals it, and it is what a mis-qualified capture produces. Catching it means reading the distinct values rather than counting them.
- Added lint WARN-052, which flags a capture group qualified by an uppercase class alone -- reached through whitespace and positional wildcards with no literal anchor. A group introduced by a literal word, sigil or key is structurally anchored and stays silent, as is an enumerated alternation of vendor tags. Advisory.
- Replaced an uppercase class with `[\w\-]` in the `extraction-patterns.md` mnemonic example, which had implied that the class was doing the qualifying when the `%` and the trailing space were.

## 1.8.7

- Added lint WARN-051: an account captured from qualifier-bearing prose with no guard against the qualifier itself being captured. An unquoted group directly after `for` or `user` returns `invalid` or `Masked` on a redacted line, and a correlation keyed on that collapses unrelated attempts from different hosts onto one fictional identity. A quote-delimited capture and a `key=` capture are both bounded and are not flagged, and a rule that guards the value anywhere is silent. Advisory rather than blocking, because the absence of a guard is inferred and a source may be known never to emit a qualifier. The check follows a bare rename stage to the capture that produced the value.
- A companion check for an `xdm.event.operation` chain terminating on a broad subsystem flag was designed and deliberately NOT shipped. The detectable signal is the terminal branch's VALUE, but the defect is in its CONDITION, and the two come apart: a chain that ends on a specific condition and assigns the generic verb correctly is indistinguishable from one that sweeps a subsystem. Separating them needs semantics the linter cannot see, so this stays documented guidance in `record-classification.md` rather than becoming a check that fires on correct rules.

## 1.8.6

Two of these describe defects that a clean lint AND a clean population audit both report as healthy.

- The post-deploy audit now counts THREE states per field, not two: a real value, the empty string, and the catch-all sentinel. A field whose extraction failed and fell back to `GOCORTEX_UNMODELLED` is non-null, non-empty and reports full population while carrying no information, so it passes every check the skill previously prescribed. `scripts/verify_rule.py --coverage` counts sentinel values separately and flags a field that is predominantly or entirely sentinel.
- Added the rule that a body capture must not anchor on a structural character that is optional. Anchoring MSG on the close of the RFC 5424 structured-data element (`"\]\s+(.+)$"`) returns null on every record whose SD is nil, because there is no bracket in the line at all; the field then falls back to its default, which is how the sentinel case above arises.
- Added a field-set diff step for a rule that REPLACES an existing one. Correlations and dashboards bind to fields, not to datasets, so a rewrite that stops emitting a field some content reads makes that content structurally incapable of firing rather than merely short of data -- and nothing detects it, because the rule lints clean, the dataset name is unchanged and row parity is perfect. The step enumerates the old rule's `xdm.*` assignments and set-subtracts the new one's.
- Made the RFC 5424 envelope captures prepend-safe. They were `^`-anchored on the reasoning that a compliant 5424 relay records itself in structured data rather than prepending a header, which is true of a compliant relay and not true of a BSD relay in a mixed estate; a prepended header then shifted every field and the capture read the relay's values. The captures now anchor on the `<PRI>VERSION ISO-8601` sequence, which is unambiguous, occurs once, and is correct for both arrival forms.
- Added the RFC 5424 field-offset table. The header fields are bare tokens, so extracting one while believing it is another produces plausible output -- APP-NAME mistaken for MSGID yields daemon names, which is why the error survives review.
- Documented the NILVALUE `-` as first-class rather than an edge case. It is permitted in any 5424 header field and vendors use it heavily; a record with APP-NAME, PROCID, MSGID and SD all nil is the standard repeated-message marker. Every header field must be tested for the dash explicitly, not merely for null, since a dash is non-null and passes every population check. Includes the nil-MSGID fallback chain and the failure it replaces, where a naive fallback produced one meaningless identity for every nil-MSGID record and put a dash in the process name.
- Added stratified sampling to workflow step 1. A `limit N` pull from a live dataset is not a sample: it returns whichever records the engine reaches first, routinely an unrepresentative minority, and a rule authored from it can look perfect on row count while modelling the wrong shape. Count by the discriminator first, then take a few records per group.
- Documented that envelope coverage and payload-structure coverage are separate figures. A feed can be almost entirely one envelope standard while only around half carries a structured payload, and the two drive different parts of the rule: the envelope drives extraction, the payload structure drives classification.
- Documented that there is no negated regex operator. `not ~=` is rejected by the server; negate the comparison as `not (<expr> ~= "...")`.
- Added a caution that a `set` verb is not by itself a configuration change. On Junos, `set cli screen-width` and `set cli screen-length` are session terminal preferences that change nothing on the device, and a feed can contain many of them and no `commit` at all. Classify on the configuration hierarchy or the commit, never on the bare verb.

## 1.8.5

Makes the both-arrival-forms requirement for syslog enforceable rather than advisory. A syslog source reaches Cortex direct off the device and behind one or more relays that prepend their own header, and one rule must model both, always.

- Promoted the prepend-fragile check from advisory WARN-047 to blocking ERR-030. A positional or `^`-anchored body capture in a syslog rule now fails lint with a non-zero exit instead of emitting a warning that could be passed over. Prepend-fragile extraction is common enough in real syslog rules that an advisory was not carrying the weight the requirement needs.
- Fixed a false positive that had to be cleared before the check could block: `^\<`, the escaped form of the envelope anchor and a common way to write it in XQL, was not recognised as a sanctioned envelope capture, so a correctly written envelope was reported as fragile. Only the unescaped `^<` was exempt.
- Added `--prepend-check` to `scripts/verify_rule.py`, and made it a required workflow step for every syslog rule. It evaluates each record twice, as supplied and with a relay header prepended, and exits 1 naming every field whose value differs, with both values shown. This is the mechanical proof of the requirement: static lint cannot establish it, because a pattern can look like a sanctioned envelope capture and still be position-dependent. The typical finding is an observer name that resolves to the origin host directly and to the relay's host behind a relay.
- Restated the requirement at the top of `references/syslog-envelope.md` and in the SKILL.md hard rules: both forms, one rule, never two rules and never only the observed form, with the two mechanisms that achieve it and the command that proves it.

## 1.8.4

Addresses a class of defect the linter cannot see: a rule can map every mandatory field, lint completely clean, and still be wrong about what the record IS.

- Added the story-claim discipline, now a hard rule. A story tag is a promise that the story's mandatory fields mean something on that record, and downstream content queries them as though populated, so tagging a record into a story it cannot fill pollutes the story. Before tagging AUTHENTICATION confirm the record can supply an actor; before tagging NETWORK confirm it can supply a peer. Records from one subsystem differ: an interface transition never carries a peer, while an SSH transport record does when the line names a client. When a record cannot fill a story it takes an honest event type and description instead.
- Extended the facility guidance from "never the operation verb" to "never gate `xdm.event.type`, `xdm.event.tags` or any mandatory story field". A single branch keying the event type on an SSH facility sweeps terminal-window errors, handshake errors, socket closes and AAA reachability changes into the authentication story.
- An `xdm.event.operation` chain must not end on a broad subsystem flag. The skill already forbade blind-defaulting to `AUTH_LOGIN`; the same applies to the generic `OPERATION_TYPE_AUTHENTICATION`. If nothing specific matches, leave the verb unset.
- The post-deploy population audit now includes a RATIO test, not only a zero test. Padding fills the mandatory set, so no field reads as 0-of-n even when most records do not belong in the story. Comparing the records claiming a story against the records carrying its defining entity exposes the gap; a large one means the classification is too broad, and the fix is upstream in `xdm.event.type` rather than another regex.
- Added a discriminator preference order: a numeric vendor event code first, then the mnemonic, then the facility as a fallback identity only, and never the message text. Matching English prose silently misses variants, because one product can phrase the same outcome several ways.
- Added Recipe 13 for an identity carried in vendor prose rather than a structured field, covering relayed sshd and PAM phrasing and quoted vendor prose that states account, address and terminal line together. Failure records resolving to many accounts from few addresses are a spraying signature that a rule which never reads the body discards entirely.
- Added a guard against redaction and qualifier tokens in a prose capture. Taking the first word after "for" in a masked sshd line yields `invalid` or `Masked`, and a correlation keyed on that collapses unrelated attempts from different hosts onto one fictional user. A null actor is the truth; a plausible fictional one is a correlation defect.
- Stated the logout convention so it is not re-decided per rule: a logout takes `OUTCOME_SUCCESS` and NO operation, because `OPERATION_TYPE` has no logout member. Asserting `AUTH_LOGIN` on a logout inflates every login count that filters on the verb.
- Documented that some products log one login twice under two event codes, from the operating-system and application layers. Both records are genuine; the consequence is that any login count doubles unless it deduplicates, and a double-logging source should be called out in the MAPPED header NOTES.

## 1.8.3

- Fixed `_raw_log` binding in `scripts/verify_rule.py`. A record carrying an explicit `_raw_log` column had that value silently overwritten with the record's JSON text, so a syslog sample handed over in its most natural form, `{"_raw_log": "<190>Jul 29 ..."}`, was verified against `{"_raw_log": "<190>Jul 29 ..."}` rather than the log line itself. The failure was plausible rather than loud: `^`-anchored patterns stopped matching and trailing captures picked up JSON syntax, which skewed field population without any error. An explicit column now wins; only a record without one has `_raw_log` synthesised, which preserves the Pattern A behaviour for a JSON-bodied dataset.
- Added `--coverage` to `scripts/verify_rule.py`. It reports, per `xdm.*` field, how many records populated it and how many of those values were the empty string, and flags any field that is entirely or predominantly empty. This is the signature of a capture that matches every record and captures nothing, which no match count reveals. It also makes sample representativeness visible, so a low population reads as a property of the sample rather than a broken mapping.
- WARN-046 no longer repeats per pipeline. A MODEL block holding several `;`-terminated pipelines, each selecting the record kind it maps, routes records rather than dropping them, so the question is whether the rule as a whole ends with a catch-all. The check now reports once for such a rule instead of once per pipeline; a thirty-pipeline rule produced thirty copies of one finding. Single-pipeline behaviour is unchanged.

## 1.8.2

- Recipe 1 could fail SILENTLY on a doubly-quoted payload. A forwarding chain that CSV-escapes the line turns `user="x"` into `user=""x""`, and the delimiter-anchored `"([^"]*)"` form then matches the zero-length gap between the quotes: it captures the empty string on every record while a coverage count reports the mapping healthy. `extraction-recipes.md` now documents the trap, gives a delimiter-agnostic default that handles bare, single-quoted and doubly-quoted values, and states that a match count is not evidence a capture works -- print real values, including a multi-word one, so a truncating non-greedy quantifier is caught.
- The syslog FACILITY is not a stable classifier. On Junos, `UI_LOGIN_EVENT`, `UI_AUTH_EVENT`, `UI_LOGOUT_EVENT` and `UI_CMDLINE_READ_LINE` each arrive under two different facilities from the same daemon. `extraction-recipes.md` and `record-classification.md` now state that the MNEMONIC is the stable identity, the facility is a fallback only for records carrying no mnemonic, and the facility must never become the operation verb. The recipe also handles a two-part facility (`%SECURITY-SSHD_SYSLOG_PRX-6-INFO_GENERAL`), which the previous single-facility pattern missed.
- Added device-local authentication topology to `authentication-mapping.md`. The existing AAA-gateway guidance covers a three-party shape (operator, AAA server, administered device) but not a device authenticating a user INTO ITSELF, where the device is both observer and target and the remote end is the source. Getting it wrong inverts every record while the linter stays clean.
- Gated placeholder padding for ENTITY fields. Padding satisfies WARN-042 completely, so a rule could assign every mandatory field, lint clean, and still hold the wrong entity or none at all. Before padding `xdm.source.ipv4`, `xdm.target.ipv4`, `xdm.*.host.hostname` or `xdm.source.user.*`, confirm the source genuinely cannot supply the value under another name or topology, then pad and record the reason in NOT MAPPED. Padding remains correct for scalars and enums the source genuinely lacks. Added the post-deploy discipline of counting each mandatory field's population, since a 0-of-n on an entity field is usually a topology error the linter cannot see.
- Corrected the `priv_lvl` banding against RFC 8907 section 9. Level `0` is `TAC_PLUS_PRIV_LVL_MIN`, an UNAUTHENTICATED session, so it bands to `PRIVILEGE_LEVEL_GUEST`; the previous guidance banded it to `PRIVILEGE_LEVEL_USER`, which asserted an authenticated principal the protocol does not claim. Level `1` is a regular authenticated session and `15` (`0x0f`) is `TAC_PLUS_PRIV_LVL_ROOT`. The levels are ordered supersets, so the guidance now bands with `>=` rather than enumerating.
- Grounded two recipes in their authoritative public sources: RFC 8907 section 8.2 states that multiple `cmd-arg` arguments may be specified and are ORDER DEPENDENT (so Recipe 12 must preserve their order), and Juniper documents the message TAG as the unique identifier of a system log message while a facility is only a grouping of messages sharing a process or condition.
- Added a consolidated AAA and network-device field crosswalk to `authentication-mapping.md`. The `priv_lvl` -> `xdm.auth.privilege_level` mapping was already documented but sat about 340 lines below the mandatory table and was missed in practice; the vendor field names an AAA or device source emits are now in one table.
- Added Recipe 12 for one value split across repeated tokens. A TACACS+ authorisation record expresses a command as one `cmd=` plus N `cmd-arg=` tokens, and mapping `cmd=` alone yields a useless fragment. `arraystring()` over a multi-match `regextract()` rebuilds the whole command; the idiom generalises to any repeated-key shape.
- Documented that one source can spell one field several ways (`priv_lvl`, `priv-lvl` and `privilege` side by side in a single dataset) and that all variants belong in one alternation.
- Documented `tag` as a reserved field name. It is rejected in SEARCH mode as well as in a rule, and it is the natural name for a `%FAC-SEV-MNEMONIC` token; `extraction-patterns.md` now shows `tmp_mnemonic` instead and explains that the `tmp_` prefix exists to avoid the whole keyword class.
